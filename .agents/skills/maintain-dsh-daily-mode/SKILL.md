# 维护日用模式

先读 [维护文档](../../../MAINTENANCE.md)，确认本次涉及的组件、作用域、程序机制和模型指导；通过其中的实现入口定位代码。项目事实集中维护在该文档，提示词及参数正文见 [模式配置](../../../cordis.patch.yml) 和相关类型定义。

## 调查与适配

从用户要求及相关调用链确定修改范围。调查 DSH 更新时，读取目标源码的 `docs/architecture.md`，区分源码版本、构建基准和运行 Host 版本；根据 imports 与配置定位上游服务、事件、工具和提示词的生产代码及直接消费者。

按功能语义决定保留、调整或撤除。上游存在等价能力时，核对作用域、持久化、结果交付、唤醒和 UI 后再移除重复实现；接口取消时寻找公开替代。纯插件无法保持的能力应明确说明具体缺口。

修改上下文时，追踪内容生成方、事件顺序、日志和最终模型请求。将上游新增的必要指导融入对应角色或工具，核对改写范围，保留任务正文、来源和路由信息。结合整套上下文判断效果，避免仅按某一段的长度决定取舍。

按受影响组件核对直接消费者：

| 组件 | 重点检查 |
|---|---|
| 模型设置与路由 | ConfigForm、modelCatalog、volatile 配置、`agent/status` 和 `agent/request` |
| Agent Control | 子会话目录、Inbox 交付、运行结束、消费记录、实例释放及等待取消 |
| 归档过滤 | 原生目录、面包屑、导航、统计和客户端模块发现 |
| 永久清理 | JSONL 编码、写入锁、启动依赖、投影缓存与工作区关联 |

注册使用 `ctx.effect()` / `ctx.on()` 并声明依赖和作用域；waterfall 使用 `next()` 委托。客户端改动同时考虑 Web 与 Desktop。

## 验证与交付

按 [构建与发布说明](../../../MAINTENANCE.md#安装构建与发布) 更新源码和产物，同步构建基准及必要的依赖、许可信息；peer 范围遵循文档中的最低版本策略。核对 bundle 加载顺序和内部客户端身份。

按改动选择能证明相关行为的检查，并复用状态未变的有效证据。上下文检查覆盖最终系统提示词、动态消息和完整工具 schema，区分主/子角色及 Goal 状态；生命周期检查关注交付、唤醒、恢复和资源释放。类型检查与构建只能证明相应工程结果，模型和界面行为需要对应的运行证据。

验证永久清理时使用可丢弃的独立数据，避免将使用者的真实会话作为测试材料。交付说明包含改动、实际验证及影响使用的限制；外部发布遵循用户已给出的授权。
